## Inventario contractual de campos y fronteras — DRAFT

## 1. Frontera general

`AlarmDefinition` representa la configuración de negocio de una regla de alarma. El frontend del ADA Command Center editará este contrato; no construirá `PlannedAlarm` ni contratos internos del runtime.

Cadena conceptual:

```text
Frontend de configuración
        ↓
AlarmDefinition
        ↓
B.2 Configuration Resolution
        ↓
PlannedAlarm + AlarmExecutionEntry
        ↓
A.3 Alarm Runtime
```

La definición no contiene clientes físicos, SharePoint/Cosmos específicos, estado runtime, leases, commits, UI layout ni código ejecutable.

## 3. Clasificación operacional

### Acordado

| Campo | Valores / tipo | Semántica |
|---|---|---|
| `kind` | `RISK | IMPACT` | Categoría informativa de la alarma. Se muestra al operador y conserva significado de negocio. |
| `business_category` | catálogo | Categoría de negocio: operacional, salud y seguridad, medio ambiente, costos, producción, mantención, u otras futuras del catálogo. |
| `color` | catálogo | Color funcional de la alarma. Actualmente existe evidencia histórica para `RED` y `YELLOW`. |
| `is_special_condition` | `bool` | Indica que la regla puede ser utilizada como condición especial por otras alarmas. No reemplaza `kind`. |

### Regla importante

`kind` e `is_special_condition` son dimensiones independientes.

```text
kind = RISK | IMPACT
is_special_condition = true | false
```

Una condición especial sigue siendo una regla completa y puede conservar su tipo Riesgo o Impacto.

## 5. Evaluación y valores inyectables

### Acordado

La definición debe permitir modificar límites, ventanas, tolerancias y otros valores relevantes **sin desplegar nuevamente código a producción**.

| Campo | Tipo conceptual | Semántica |
|---|---|---|
| `evaluator_key` | `str` | Identifica un evaluator productivo, versionado y probado. |
| `evaluation.parameters` | mapa tipado | Valores inyectables consumidos por el evaluator. |

Ejemplo conceptual:

```python
evaluation = {
    "evaluator_key": "sustained_high_pressure",
    "parameters": {
        "high_limit": 85.0,
        "minimum_duration_seconds": 120,
        "deadband": 2.5,
    },
}
```

### Invariante

Los parámetros son datos. No se permite código, expresiones Python, lambdas ni fórmulas ejecutables provenientes de configuración.

Una condición especial puede usar un evaluator completamente diferente al de la alarma principal. No se modela como “el mismo evaluator con otro límite”.

## 7. Management y reaparición

### Comportamiento base acordado

Una gestión aceptada oculta la ocurrencia gestionada. Este comportamiento es del motor y **no se configura por regla**.

Si la condición principal continúa activa, la alarma puede volver a mostrarse por dos mecanismos independientes:

```text
GESTIONADA + CONDICIÓN PRINCIPAL SIGUE ACTIVA
                │
                ├── vencimiento de tiempo ─────────┐
                │                                  │
                └── condición especial activa ─────┤
                                                   ↓
                                              REAPARECE
```

Cuando existen ambos mecanismos, la semántica acordada es **OR**: el primero que ocurra fuerza la reaparición.

### Campos acordados

| Campo | Tipo conceptual | Semántica |
|---|---|---|
| `operator_bucket` | `str | None` | Bucket/agrupación operacional destinada al operador cuando aplique. |
| `reappearance.after_seconds` | `int | None` | Tiempo tras gestión antes de permitir/forzar reaparición si la condición sigue activa. |
| `reappearance.special_condition_keys` | `tuple[str, ...]` | Una o más reglas marcadas `is_special_condition=true` que pueden forzar reaparición. |
| `continue_escalation_clock_when_hidden` | `bool` | Define si el reloj de escalamiento continúa mientras la ocurrencia gestionada está oculta. |
| `use_message_management_override` | `bool` | Conserva la capacidad histórica de permitir políticas asociadas a mensajes/contenido cuando exista esa función. |

### Invariantes

- Las `special_condition_keys` deben apuntar a reglas existentes y activas marcadas como `is_special_condition=true`.
- Si hay múltiples condiciones especiales, cualquiera de ellas puede disparar la reaparición.
- El timer o una condición especial sólo pueden hacer reaparecer la ocurrencia si la condición principal de la alarma continúa activa.
- Si la condición principal normalizó, un timer anterior no debe resucitar la alarma.
- Una activación posterior a una normalización corresponde a una nueva ocurrencia, no a reaparición de la ocurrencia gestionada.

## 9. Escalamiento entre herramientas

### Acordado

El escalamiento fuente debe conservar una secuencia explícita y no reducirse prematuramente a `AlarmRouting`.

Cada paso puede declarar:

| Campo | Tipo | Semántica |
|---|---|---|
| `step_order` | `int > 0` | Orden del paso. |
| `target_tool_key` | `str` | Tool destino. |
| `is_enabled` | `bool` | Habilita/deshabilita el paso. |
| `wait_seconds_from_previous_step` | `int | None` | Tiempo desde el paso anterior. |

`origin_tool_key` define dónde nace la alarma.

B.2 resolverá esta configuración hacia el `AlarmRouting` ejecutable utilizado por el motor.

Las reglas C1/C2/C3 ya calificadas deben preservarse durante esa resolución.

## 11. Ownership de Tool Configuration

### Decisión acordada

**Cada herramienta es dueña de su propia configuración. Alarm Configuration no define ni duplica Tools, Components, Subcomponents ni el tipo/tier de herramienta.**

Cada Tool debe publicar/proyectar al menos la información necesaria para que otros consumidores puedan descubrirla y referenciarla:

```text
Tool Configuration
├── tool_key
├── tool_type / tool_tier
│   ├── process
│   ├── integrated_operations
│   └── strategic
├── components[]
│   ├── component_key
│   └── ...
└── subcomponents[]
    ├── subcomponent_key
    ├── parent_component_key
    └── ...
```

Los detalles adicionales pertenecen a cada Tool y no se incorporan automáticamente a Alarm Definition.

### Consumo desde Cosmos DB

La configuración publicada por cada Tool se proyectará a Cosmos DB cuando corresponda.

**Alarm Configuration consume esa proyección para descubrir y absorber referencias disponibles**, por ejemplo:

```text
Cosmos DB — Tool Configuration Projection
               │
               ▼
Alarm Configuration / Command Center
               │
               ├── tools existentes
               ├── tipo/tier de cada tool
               ├── components existentes
               └── subcomponents existentes
```

Esto permite que el editor/configurador de alarmas ofrezca únicamente referencias cuya información exista en la proyección disponible.

### Reglas de ownership

- `tool_key` pertenece a la Tool.
- `tool_type/tool_tier` pertenece a la Tool.
- `component_key` pertenece a la Tool.
- `subcomponent_key` pertenece a la Tool.
- La relación `subcomponent → parent component` pertenece a la Tool.
- Alarm Configuration sólo almacena referencias a esos IDs.
- No se mantienen catálogos manuales duplicados de Tools/Components/Subcomponents dentro del dominio de alarmas.
- La ausencia de una referencia en la proyección disponible de Cosmos implica que no puede considerarse resoluble por Alarm Configuration hasta que la Tool publique/proyecte esa información.
- B.2 será responsable de validar las referencias al resolver una revisión de configuración.
- Cosmos funciona aquí como plano de proyección/consumo; no cambia el ownership de la configuración, que sigue perteneciendo a cada Tool.

## 12. Fronteras con frontend, configuración y runtime

### Frontend

El frontend:

- edita/captura `AlarmDefinition`;
- consume catálogos/proyecciones para selectors y validaciones;
- no crea `PlannedAlarm`;
- no es dueño de las reglas de lifecycle;
- no define Tools/Components/Subcomponents.

### B.1 — Canonical Alarm Definition

Define:

- campos;
- tipos;
- invariantes locales;
- relaciones declarativas;
- IDs estables.

No conoce SharePoint, Cosmos físico, Dash, Flask ni loaders.

### B.2 — Configuration Resolution

Debe resolver/validar:

- revisión de configuración;
- referencias entre reglas;
- `special_condition_keys`;
- Tool/Component/Subcomponent contra las proyecciones disponibles;
- escalamiento;
- contenido referenciado;
- definición → `PlannedAlarm`;
- parámetros → `AlarmExecutionEntry`.

### A.3 — Alarm Runtime

Consume contratos ya resueltos y conserva:

- lifecycle;
- evaluación;
- prioridad;
- management;
- reaparición;
- escalamiento;
- persistencia/durabilidad;
- recovery/drain.
