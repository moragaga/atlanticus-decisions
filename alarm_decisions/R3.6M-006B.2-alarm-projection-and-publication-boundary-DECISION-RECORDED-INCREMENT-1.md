# R3.6M-006B.2 — Alarm Projection Boundary

## Live Alarm Projection vs Management Projection

**Status:** DECISION RECORDED — INCREMENT 1  
**Date:** 2026-09-03  
**Scope:** ADA Command Center — operational backend  
**Context:** Configuration Resolution / projection / publication boundary

## 1. Decision

ADA Command Center will maintain two distinct operational projections with different purposes and lifecycles:

1. **Alarm Live Projection** — current operational state of alarms.
2. **Alarm Management Projection** — historical projection of user management actions over alarms.

They are not interchangeable and must not be merged into a single projection/job.

## 2. Alarm Live Projection

The Live Projection answers: **what is operationally happening now?**

It is produced from the current alarm engine state after evaluation, lifecycle, priority, management and deactivation have been resolved.

A Rule whose physical condition remains active continues to belong to the live flow even when it is currently managed or deactivated.

Therefore:

- `managed = true` does **not** remove the alarm from the live projection.
- `deactivated = true` does **not** mean the physical condition is inactive.
- the live projection may expose current management/deactivation state as attributes of the live occurrence.
- the Web can use those attributes for current operational views and filters.

## 3. Priority before projection

The Live Projection must respect the engine's resolved priority.

If three Rules in the same `priority_group` are physically active:

```text
Rule 1  ACTIVE / PREDOMINANT
Rule 2  ACTIVE / ECLIPSED
Rule 3  ACTIVE / ECLIPSED
```

only **Rule 1** is delivered as the current operational alarm for that group.

The Web must never receive all physically active Rules and resolve priority itself.

Priority is a backend engine responsibility.

## 4. Multiple Web surfaces from the same live flow

A single live occurrence can feed more than one Web surface without becoming multiple alarm entities.

Typical consumers include:

```text
Alarm Live Projection
├── Alarm Surface / layout
├── Active Alarms Modal
├── current managed-state filtering
└── current deactivated-state filtering
```

Example: a predominant active Rule may simultaneously be visible in the layout and in the Active Alarms Modal. The modal may expose a richer payload and a shortcut to management, while both represent the same live occurrence.

This does not imply four independent backend scopes such as `LAYOUT`, `ACTIVE_ALARMS`, `MANAGED_ALARMS`, and `DEACTIVATED_ALARMS`.

Managed and deactivated are current-state dimensions of the live alarm, not separate historical projections.

## 5. Live delivery payload

The Live Projection should contain enough resolved information for operational Web consumption without requiring the Web to re-resolve configuration catalogs.

Depending on the consuming surface, the projection may expose:

- `family_key`, `alarm_key`, `occurrence_id`;
- current operational status and priority disposition;
- title, display name and materialized cause text;
- kind, criticality, business category and operational areas;
- semantic alarm color (`RED` / `YELLOW`), never CSS values;
- resolved visual targets;
- associated active Messages;
- current management state;
- current deactivation state and `effective_until` when applicable;
- effective management/deactivation capabilities required by the current UI.

The Web consumes resolved operational data. It does not interpret `AlarmDefinition`, resolve Message catalogs, determine priority, or validate deactivation authorization.

## 6. Alarm Management Projection

The Management Projection answers a different question: **what actions did users perform over alarms, and how did those management flows close?**

It is a separate job/projection built from durable management history, not from the current live alarm list.

Its source domain includes, as applicable:

- `ManagementAction`;
- `ManagementEffect`;
- `DeactivationRequest`;
- `DeactivationDecision`;
- `DeactivationEffect`;
- durable Journey / management records.

It is oriented to closed/historical management flows and user actions.

It does **not** determine which alarm currently predominates and does not replace the Live Projection.

## 7. Architectural boundary

```text
                         ALARM ENGINE
                              │
                 ┌────────────┴────────────┐
                 ▼                         ▼
          Current engine state       Durable management records
                 │                         │
                 ▼                         ▼
       Alarm Live Projection      Management Projection Job
                 │                         │
                 ▼                         ▼
      Current operational Web      Closed management history
```

The two projections may reference the same `AlarmIdentity` / `occurrence_id`, but they have different responsibilities, schemas, cadence and retention.

## 8. Impact on R3.6M-006B.2

B.2 Configuration Resolution does **not** implement either projection job.

B.2 must instead produce a `ResolvedAlarmConfiguration` / `ResolvedAlarm` rich enough that downstream Live Delivery can materialize its snapshot without returning to SharePoint, Cosmos or unresolved catalogs.

The Management Projection remains a later, separate increment based on durable management records.

## 9. Frozen invariants from this decision

- One live occurrence remains one occurrence even if consumed by multiple Web surfaces.
- Managed active alarms remain in the live flow.
- Deactivated alarms whose physical condition remains active remain part of the live state.
- Priority is resolved before Live Projection.
- Eclipsed Rules are not published as the current operational alarm for their group.
- Web does not resolve alarm priority.
- Web does not resolve Message references or business configuration.
- Live Projection represents **current operational state**.
- Management Projection represents **historical user management activity**.
- Management Projection is a separate job and must not be used as the source of truth for the current live alarm surface.

## 10. Out of scope for this record

This decision does not freeze:

- physical Cosmos container count or partitioning;
- concrete Live Projection schema version;
- Management Projection schema version;
- projection cadence;
- retention policy;
- query/index strategy;
- frontend modal implementation details.

Those remain for their corresponding implementation increments.

## Increment 1 — Publication, reconciliation and materialization pipeline

This increment extends the previously recorded Live Alarm Projection / Management Projection boundary.

**Core principle:** SharePoint remains the authority and historical source, but operational publication is explicit. Draft or transient SharePoint state does not automatically become Runtime or Delivery configuration.

## 11. Tool reconciliation and confirmed Tool catalog

ADA Command Center may use multiple named Cosmos connections. Each participating Tool publishes the same Tool projection contract in its configured Cosmos environment.

The administrative Tool workflow reconciles discovered projections against the confirmed Tool history maintained in SharePoint.

Important states include:

- a Cosmos connection may exist without yet exposing a usable Tool;
- a Tool projection may exist but differ from the last confirmed SharePoint reconciliation;
- a Tool expected by confirmed history may disappear, become malformed, or become unavailable;
- two connections publishing the same `tool_key` are a reconciliation conflict and must not be resolved silently.

Only reconciled and confirmed Tools become available to Alarm Configuration.

```text
SharePoint Tool history
        +
Named Cosmos Tool projections
        |
        v
Tool Reconciliation
        |
        v
Confirmed Tool Catalog
        |
        v
Alarm Configuration validation
```

Alarm Rule validation does not discover Tool topology directly from arbitrary Cosmos connections.

## 12. Rule authoring, validation and publication are distinct

An Alarm Rule may be saved in SharePoint even when a current dependency is invalid or unavailable. This preserves history and allows administration to diagnose drift.

```text
SAVE
→ preserves authored Rule and history

VALIDATE
→ resolves references/invariants and produces findings

PUBLISH CANDIDATE
→ marks a revision for operational materialization

EFFECTIVE
→ Runtime has successfully adopted the materialized revision
```

Therefore, a saved Rule may have validation findings without immediately stopping the currently effective alarm process.

## 13. Alarm Configuration Materialization Job

A separate periodic job checks whether the published Alarm Configuration revision or the Confirmed Tool Catalog revision changed.

The exact cadence is not frozen by this record.

Normal path:

```text
read published Alarm revision
read confirmed Tool Catalog revision
        |
        v
compare with last materialized/effective pair
        |
        +-- unchanged --> finish
        |
        `-- changed --> load candidate snapshots
                        |
                        v
                       B.2
                        |
                        v
                  Validation Report
```

The materialization job owns candidate acquisition and pre-validation.

The Alarm Runtime does **not** become a:

- SharePoint downloader;
- Tool discovery process;
- Message catalog resolver;
- cross-configuration validator.

## 14. Invalid candidate and last-known-good behavior

A candidate with a broken Tool, Message, evaluator, Special Condition, priority invariant, visual target or other B.2 dependency is not partially cleaned and published as if the affected Rule had been removed.

Example:

```text
Effective:
ALARM-R18 / TOOL-R42
GREEN

Candidate:
ALARM-R19 / TOOL-R43
INVALID

Finding:
process-sag missing from confirmed Tool catalog

Result:
- reject/quarantine candidate R19/T43 for operation
- retain effective R18/T42
- record the finding for administration/diagnosis
```

**Critical invariant:**

```text
INVALID != REMOVED
```

Silently dropping the Rule could make Runtime close an occurrence or episode because of a broken dependency rather than an intentional removal.

## 15. Disabled and invalid are different

```text
DISABLED
→ valid configuration
→ publish to Runtime materialization
→ Runtime can close/reconcile existing state correctly

REMOVED
→ intentional absence from target configuration
→ Runtime adoption may close/remove state

INVALID
→ candidate cannot become operational
→ retain last-known-good effective revision
```

A Rule with `is_active = false` therefore remains represented in the Runtime-oriented materialization.

## 16. Two operational materializations from one validated resolution

A candidate that passes B.2 produces two purpose-specific projections from the same validated resolution.

### Runtime Configuration Projection

Optimized for engine execution and adoption.

Typical content:

- defined Rule identities;
- `is_active`;
- `PlannedAlarm` or equivalent executable contract;
- parameters;
- evaluator reference;
- priority/routing;
- adoption-relevant configuration;
- runtime management/reappearance inputs.

Disabled Rules remain represented here.

### Delivery Configuration Projection

Optimized for Live Projection enrichment.

Typical content:

- display name;
- title and cause content contract;
- semantic alarm color;
- kind, criticality, business category and operational areas;
- resolved Messages and deactivation capability;
- resolved visual targets;
- Process projection mode.

It does not need evaluator callables, DataRequirements, lifecycle state or adoption machinery.

Both materializations carry the same `resolution_key`, composed at minimum from:

```text
alarm_configuration_revision
+
confirmed_tool_catalog_revision
```

They are not two independent truths.

## 17. Runtime adoption controls EFFECTIVE

Successful B.2 materialization produces a `READY` candidate.

It does **not** automatically advance the operational effective revision.

```text
Validated candidate
        |
        +--> Runtime Projection   READY
        `--> Delivery Projection  READY
                 |
                 v
        Runtime adoption succeeds
                 |
                 v
     effective_resolution_key advances
```

The materializer answers:

> Is the candidate configuration coherent?

Runtime adoption answers:

> How does the current occurrence/episode/durable state evolve into this valid target?

## 18. Delivery follows Runtime

Delivery must never enrich live state with a configuration revision that Runtime has not adopted.

```text
AlarmRuntimeState
effective_resolution_key = ALARM-R19 / TOOL-R43
        +
Delivery Configuration Projection
resolution_key = ALARM-R19 / TOOL-R43
        |
        v
Alarm Live Projection
```

This guarantees revision alignment between engine semantics and Web enrichment.

## 19. Validation and reconciliation diagnostics

Failed Tool reconciliation and failed Alarm Configuration candidates produce diagnostics for the administrative surface without replacing the effective operational revision.

Relevant findings include:

- Tool expected by confirmed history but missing from its projection;
- Tool projection differs from the last confirmed reconciliation;
- duplicate `tool_key` across named Cosmos connections;
- Rule references an unavailable Tool/Component/Subcomponent;
- Rule references a missing/invalid Message, evaluator or Special Condition;
- candidate fails priority, routing or other cross-Rule invariants.

## 20. Updated architectural boundary

```text
                         SHAREPOINT
                    Authoring + history
                +---------+---------+
                |                   |
            Tool history        Alarm history
                |                   |
                v                   |
       Named Cosmos Tool            |
          projections               |
                |                   |
                v                   |
        Tool Reconciliation         |
                |                   |
                v                   |
       Confirmed Tool Catalog       |
                +---------+---------+
                          |
                          v
          Alarm Configuration Materialization Job
                          |
                         B.2
                          |
               +----------+----------+
               |                     |
               v                     v
      Runtime Projection      Delivery Projection
             READY                  READY
               |                     |
               v                     |
         Runtime Adoption             |
               |                     |
               +----------+----------+
                          |
              effective_resolution_key
                          |
                          v
                 Alarm Live Projection
```

Durable management history remains separate and later feeds the **Management Projection Job** defined by the original decision.

## 21. Frozen invariants added by Increment 1

- SharePoint remains authority/history but may contain drafts or transient unpublished states.
- Operational consumption uses reconciled/published projections, not arbitrary draft state.
- Alarm Configuration consumes a Confirmed Tool Catalog, not direct Tool discovery during Rule resolution.
- Saving a Rule does not imply that the Rule is valid or operationally published.
- An invalid candidate does not replace the current effective configuration.
- `INVALID` is never silently converted into `REMOVED`.
- Disabled Rules remain represented for Runtime adoption/reconciliation.
- One validated resolution produces both Runtime and Delivery materializations.
- Runtime and Delivery materializations share the same `resolution_key`.
- A materialized candidate is `READY` until Runtime successfully adopts it.
- Runtime owns transition/adoption of existing operational state; the materializer owns candidate validation.
- Delivery follows Runtime `effective_resolution_key` and must not lead the engine revision.
- Tool reconciliation conflicts and configuration validation failures remain observable without destabilizing the last-known-good Runtime.

## 22. Still out of scope

This increment does not freeze:

- exact polling cadence for Tool reconciliation or Alarm Configuration materialization;
- event-driven trigger mechanism;
- whether Service Bus is introduced;
- physical Cosmos database/container/partition layout;
- exact revision/fingerprint document schemas;
- retention of `READY`, `REJECTED` and historical materializations;
- administrative UI implementation/status vocabulary;
- final schema versions for Runtime and Delivery Configuration projections.
