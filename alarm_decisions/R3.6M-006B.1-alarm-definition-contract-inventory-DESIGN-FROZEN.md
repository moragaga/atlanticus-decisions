## 1. Frontera contractual

`AlarmDefinition` representa la configuración canónica de negocio de una Rule de alarma.

Cadena conceptual:

```text
Alarm Configuration
        |
        v
AlarmDefinition
        |
        v
B.2 - Configuration Resolution
        |
        +--> validación de referencias externas
        +--> Tool Configuration Projection
        +--> Message Catalog
        +--> evaluator registry
        |
        v
PlannedAlarm + AlarmExecutionEntry
        |
        v
A.3 - Alarm Runtime
```

B.1 define:

- campos;
- tipos;
- enums;
- subcontratos;
- IDs estables;
- invariantes locales;
- formas de referencia.

B.1 no conoce:

- clientes de Cosmos DB;
- SharePoint;
- Key Vault;
- Dash o Flask;
- layout físico del frontend;
- loaders;
- sessions web;
- estado runtime;
- commits/WAL;
- leases;
- código ejecutable proveniente de configuración.

B.2 valida las referencias que requieren conocer otras Rules, Tools, Components, Subcomponents, Messages o evaluators.

## 2. Terminología: Rule, Alarm y Occurrence

Para evitar ambigüedad:

```text
Rule
-> definición/configuración estable de una alarma.

AlarmDefinition
-> contrato canónico editable de esa Rule.

PlannedAlarm
-> forma resuelta y ejecutable consumida por el motor.

Occurrence
-> activación concreta de una Rule en runtime.

Episode
-> contexto de lifecycle compartido dentro de un priority_group.
```

Cuando este documento habla de propiedades como prioridad, visual targets, mensajes o evaluators, se refiere a una **Rule específica**, salvo que se indique expresamente que la regla opera sobre una occurrence runtime.

## 3. Identidad y nombres

### 3.1 Identidad estable

La identidad canónica continúa siendo:

```python
AlarmIdentity(
    family_key: str,
    alarm_key: str,
)
```

Semántica:

```text
family_key
-> familia lógica de la Rule.

alarm_key
-> ID estable e inmutable de la Rule.
-> corresponde semánticamente al antiguo rule_key de falarm.
-> se usa para lifecycle, persistence, referencias y relaciones.
```

No se reintroduce `rule_key` como un cuarto concepto.

### 3.2 Nombres

```text
rule_name
-> nombre técnico/semántico de la Rule.
-> editable.
-> requerido.
-> único dentro de su family.

display_name
-> nombre humano visible.
-> editable.
-> requerido.
```

Un mismo `rule_name` puede existir en familias distintas.

Ejemplo:

```text
family=SAG,     rule_name=high_pressure
family=CRUSHER, rule_name=high_pressure
```

No puede existir dos veces dentro de la misma family.

### 3.3 Contenido base

El contenido base de la Rule queda:

```text
title: str
cause_template: str
```

`title` es estático. No es template.

`cause_template` puede incorporar información dinámica materializada desde la evaluación/evidence.

Ejemplo conceptual:

```text
title:
"Alta presión descarga SAG"

cause_template:
"Presión {pressure} supera el límite {limit}"
```

B.1 valida que ambos sean no vacíos, pero no valida que los placeholders del `cause_template` coincidan con la salida de un evaluator específico.

### 3.4 Campos retirados de B.1

Quedan fuera del contrato actual:

```text
rule_key
content_key
title_template
image_key
ImageDefinition
```

Las imágenes están completamente diferidas para otra iteración.

## 4. Clasificación operacional

Campos:

```text
kind: RISK | IMPACT
criticality: C1 | C2 | C3
business_category
operational_areas
color
is_special_condition
```

### 4.1 Kind

```text
RISK
IMPACT
```

`kind` es una dimensión de negocio y permanece independiente de `is_special_condition`.

### 4.2 Criticality

```text
C1
C2
C3
```

La criticality afecta routing/escalamiento y mantiene semántica estructural en Adoption.

### 4.3 Business category

`business_category` pertenece al catálogo canónico de negocio y cada Rule declara exactamente una categoría:

```python
class BusinessCategory(StrEnum):
    ECOLOGY = "ECOLOGY"
    PRODUCTIVITY = "PRODUCTIVITY"
    SAFETY_HEALTH = "SAFETY_HEALTH"
    COSTS = "COSTS"
```

Semántica:

```text
ECOLOGY
-> Medio ambiente natural: ecosistemas, flora, fauna, biodiversidad e impactos ambientales.
-> Se evita ENVIRONMENT para no confundir esta categoría de negocio con deployment/runtime environments o variables de entorno.

PRODUCTIVITY
-> Productividad.

SAFETY_HEALTH
-> Seguridad y salud.

COSTS
-> Costos.
```

No se mantienen aliases ni categorías históricas adicionales. Ampliar el catálogo requiere una decisión contractual posterior explícita.

### 4.4 Operational areas

```python
class OperationalArea(StrEnum):
    MINE = "MINE"
    PLANT = "PLANT"
```

La Rule declara una o más áreas:

```text
(MINE,)
(PLANT,)
(MINE, PLANT)
```

No existe un valor artificial `BOTH`.

Invariantes locales:

- mínimo una área;
- sin duplicados.

### 4.5 Color

`color` es parte de la definición operacional de negocio de cada Rule, no un token CSS ni un valor derivado automáticamente de `criticality`, `kind` o del estado runtime.

El catálogo canónico queda congelado como:

```python
class AlarmColor(StrEnum):
    RED = "RED"
    YELLOW = "YELLOW"
```

## 5. Activación y visibilidad

### 5.1 is_active

```python
is_active: bool
```

Semántica:

```text
true
-> Rule participa de la sesión de evaluación.

false
-> Rule permanece definida, pero sale del flujo ejecutable.
-> si existe una occurrence abierta, se cierra como configuración deshabilitada.
```

Deshabilitar una Rule no resetea toda la family ni todo el priority_group.

### 5.2 visibility_mode

```text
VISIBLE
TRACE_ONLY
```

Semántica:

```text
VISIBLE
-> puede ser proyectada por Delivery.

TRACE_ONLY
-> continúa evaluándose y trazándose.
-> Delivery no la considera para proyección operacional visible.
```

`TRACE_ONLY` no obliga a borrar mensajes, targets, routing ni configuración.

## 6. Evaluación

Cada Rule declara:

```text
evaluator_key
parameters
```

### 6.1 evaluator_key

```python
evaluator_key: str
```

Identifica la lógica productiva que evalúa la Rule.

La resolución runtime utiliza:

```text
family_key + evaluator_key
-> AlarmEvaluatorContract
-> evaluator + DataRequirements
```

### 6.2 parameters

Tipo congelado:

```python
Mapping[str, str | float | bool]
```

Permitidos:

```text
str
float
bool
```

No permitidos:

```text
int
None
list
tuple como valor
dict anidado
expresiones
código ejecutable
```

Un valor numérico entero se expresa como float, por ejemplo:

```text
120.0
```

Los parámetros pertenecen localmente a cada Rule. No existe un catálogo global `ParameterSetDefinition`.

B.1 valida forma y tipos. El evaluator/desarrollador es dueño de los nombres esperados y de su semántica.

## 7. Priority group y prioridad total

Cada Rule declara:

```text
priority_group: str
priority_order: int
```

### 7.1 priority_group

Define el grupo donde la Rule participa del lifecycle y compite operacionalmente con otras Rules relacionadas.

El antiguo `scope_key` no se conserva como campo paralelo. Su responsabilidad evolucionó hacia `priority_group`.

### 7.2 priority_order

Existe **una sola secuencia total de prioridad dentro de cada `priority_group`**.

Esto aplica por igual a:

- Rules normales;
- Rules marcadas `is_special_condition=true`.

No existe:

```text
normal_priority
special_condition_priority
```

Ni pueden existir dos Rules con el mismo `priority_order` dentro de un grupo.

Ejemplo válido:

```text
priority_group = SAG_PRESSURE

1 -> Special Condition A
2 -> Rule B
3 -> Special Condition C
4 -> Rule D
5 -> Rule E
```

La condición especial no tiene una liga separada.

B.1 valida:

```text
priority_group no vacío
priority_order > 0
```

B.2 valida sobre la revisión completa:

```text
priority_order único dentro del group
invariantes IMPACT/RISK vigentes
```

La secuencia no necesita ser físicamente contigua para que el motor funcione, aunque el panel de configuración puede presentarla visualmente como una lista ordenada.

## 8. Special Conditions

### 8.1 Naturaleza

Una Special Condition no es un tercer `AlarmKind`.

Es una Rule normal con:

```python
is_special_condition: bool
```

Una Rule especial conserva todos los demás contratos:

```text
kind
criticality
evaluator
parameters
priority
routing
management
targets
etc.
```

### 8.2 Comportamiento normal

Mientras una Special Condition no tenga un ManagementEffect especial activo:

```text
-> evalúa normalmente
-> compite normalmente
-> usa el mismo priority_order
-> puede ser predominante o eclipsada
-> se proyecta como cualquier Rule conforme a Delivery
```

### 8.3 Efecto especial al ser gestionada

Cuando una Special Condition es gestionada y corresponde a la Special Condition predominante aplicable del `priority_group`, su ManagementEffect adquiere semántica especial:

```text
SPECIAL CONDITION gestionada
        |
        v
SPECIAL CASCADE
        |
        +--> bloquea todas las demás Rules activas
             del mismo priority_group
```

La cascada especial no se limita a `RISK`. Su alcance conceptual es el resto de Rules activas del grupo.

Sólo la Special Condition predominante debe poder ejercer esa cascada, evitando cascadas contradictorias entre múltiples Special Conditions.

### 8.4 Alcance de grupo

Una Special Condition es estrictamente local a su `priority_group`. Puede coexistir con otras Special Conditions dentro de una misma Family, pero cada una participa únicamente en el grupo al que pertenece.

Por tanto, una Rule sólo puede referenciar una Special Condition para reappearance cuando ambas pertenecen simultáneamente a:

```text
la misma family
AND
el mismo priority_group
```

No es válido reutilizar una Special Condition:

```text
entre Families distintas
ni
entre priority_groups distintos de una misma Family
```

Esta restricción preserva la prioridad interna y el alcance de la Special Cascade. La comprobación es responsabilidad de B.2 porque requiere conocer la revisión completa.

### 8.5 Retorno al flujo normal

Cuando termina su ManagementEffect:

```text
-> Special Cascade termina
-> la Rule vuelve al flujo normal
-> vuelve a competir usando priority_order
```

No pierde `is_special_condition`; simplemente deja de ejercer su efecto especial.

### 8.6 Desactivación y retorno

Si una Special Condition está gestionada y además es desactivada temporalmente, al terminar la desactivación:

```text
si la condición principal sigue activa
-> reaparece inmediatamente
-> no espera el tiempo residual del timer de reappearance anterior
```

Ejemplo:

```text
10:00 management
      reappearance programado para 11:00

10:10 deactivation hasta 10:30

10:30 expira deactivation
      condición sigue activa
      -> reaparece a las 10:30
```

## 9. Management y reappearance

Management aceptado oculta la occurrence gestionada.

La occurrence puede reaparecer únicamente si su condición principal continúa activa.

Contrato:

```python
ReappearanceDefinition(
    after_minutes: int | None,
    special_conditions: tuple[AlarmIdentity, ...],
)
```

No existe un campo `enabled`; la capacidad se deduce:

```text
after_minutes=None
special_conditions=()
-> sin reappearance configurado
```

### 9.1 Reappearance por tiempo

La unidad canónica es **minutos**.

```text
20  -> 20 minutos
60  -> 1 hora
180 -> 3 horas
```

Invariante:

```text
after_minutes is None
OR
after_minutes > 0
```

No se define un máximo artificial.

### 9.2 Reappearance por condiciones especiales

`special_conditions` contiene referencias estables:

```python
AlarmIdentity(
    family_key=...,
    alarm_key=...,
)
```

Nunca `rule_name` ni `display_name`.

Puede contener cero, una o múltiples condiciones especiales.

Si hay múltiples:

```text
SC1 OR SC2 OR SC3
```

cualquiera puede disparar reappearance.

### 9.3 Regla principal

```text
managed occurrence
AND main condition remains active
AND (
    after_minutes elapsed
    OR any referenced special condition is active
)
-> REAPPEAR
```

Si la condición principal normaliza:

```text
-> termina la occurrence
-> timer viejo y Special Conditions no pueden resucitarla
```

Una activación posterior es una nueva occurrence.

### 9.4 Cambio de after_minutes durante una gestión

El cambio aplica a la occurrence gestionada actual.

Ejemplo:

```text
management a las 10:00
after_minutes = 60
due = 11:00

a las 10:30:
after_minutes = 120
-> nuevo due = 12:00
```

Si el nuevo valor ya venció:

```text
a las 10:30:
after_minutes = 20
nuevo due teórico = 10:20
-> reaparece inmediatamente a las 10:30
```

Esto es semántica deseada y requiere reconciliación del ManagementEffect durable en el engine.

### 9.5 Escalamiento mientras está oculta

No existe:

```text
continue_escalation_clock_when_hidden
```

como configuración.

Regla base del motor:

```text
Management oculta la Rule
!=
Routing se detiene
```

El reloj de escalamiento continúa siempre.

## 10. Message Catalog

Los mensajes son contratos reutilizables, pero su universo se particiona por scope.

```text
Message Catalog
├── GLOBAL
│   ├── G1
│   └── ...
├── FAMILY_A
│   ├── A1
│   └── ...
└── FAMILY_B
    ├── B1
    └── ...
```

`GLOBAL` no es una AlarmFamily. Es un scope reservado del catálogo de mensajes.

### 10.1 MessageDefinition

Conceptualmente:

```python
MessageDefinition(
    message_key: str,
    scope: GLOBAL | FAMILY,
    family_key: str | None,
    display_text: str,
    is_active: bool,
    deactivation_override: MessageDeactivationDefinition | None,
)
```

Invariantes locales:

```text
GLOBAL
-> family_key = None

FAMILY
-> family_key requerido
```

`message_key` es identidad estable. El texto no define identidad.

Dos Messages pueden tener el mismo `display_text` si sus contratos contextuales son distintos.

### 10.2 Selección por Rule

Cada Rule almacena explícitamente:

```python
message_keys: tuple[str, ...]
```

Una Rule de `FAMILY_A` puede seleccionar:

```text
GLOBAL
+
FAMILY_A
```

Nunca mensajes de `FAMILY_B`.

Una Rule puede tener:

```text
message_keys=()
```

Un nuevo Message GLOBAL creado después no modifica silenciosamente Rules existentes. Sólo pasa a estar disponible para selección futura.

## 11. Deactivation

La desactivación es una capacidad ofrecida al operador. **El operador siempre decide** si desactivar y hasta cuándo, dentro del máximo efectivo permitido.

No existe:

```text
seleccionar Message -> desactivación automática
```

### 11.1 Default de la Rule

Conceptualmente:

```python
AlarmDeactivationDefinition(
    enabled: bool,
    max_duration_hours: int | None,
    approval_required: bool,
)
```

Invariantes:

```text
enabled=false
-> max_duration_hours=None
-> approval_required=false

enabled=true
-> max_duration_hours requerido
-> 1 <= max_duration_hours <= 12
```

El máximo de 12 horas corresponde al máximo configurable de un turno de 12 horas.

El máximo efectivo se resolverá posteriormente:

```text
effective_until
=
min(
    operator_selected_until,
    now + configured_max_duration,
    shift_end,
)
```

B.1 no resuelve el fin de turno.

### 11.2 approval_required

`approval_required` significa que, después de que el operador solicita la desactivación, existe una aprobación/decisión adicional.

No significa que la propia decisión inicial del operador sea opcional.

### 11.3 Override de Message

Un Message puede definir:

```python
MessageDeactivationDefinition(
    enabled: bool,
    max_duration_hours: int | None,
    approval_required: bool,
)
```

Precedencia congelada:

```text
message.deactivation_override is None
-> usar default de la Rule

message.deactivation_override existe
-> reemplaza COMPLETAMENTE el default de la Rule
```

No se mezclan campos uno por uno.

Ejemplos:

```text
Rule: enabled=true, max=2h
Message: override enabled=true, max=7h
-> 7h, limitado por fin de turno

Rule: enabled=true, max=2h
Message: override=None
-> 2h

Rule: enabled=true, max=2h
Message: override enabled=false
-> no ofrecer deactivation en ese contexto
```

Una gestión/desactivación ya materializada conserva su `effective_until`; un cambio posterior de MessageDefinition o default aplica sólo a decisiones futuras.

## 13. Visual targets

Cada Rule puede declarar uno o más targets de proyección.

Shape conceptual común:

```text
AlarmVisualTarget
├── tool_key
├── component_keys[]
├── subcomponents[]
│   ├── owner_component_key
│   └── subcomponent_key
└── process_projection_mode
```

La identidad de un Subcomponent es:

```text
(owner_component_key, subcomponent_key)
```

### 13.1 Integrated Operations

En Operaciones Integradas:

```text
Component
-> determina dónde se posiciona/organiza la alarma.

Subcomponents
-> elementos que reciben el color/afectación visual.
```

Una Rule puede afectar múltiples Components y múltiples Subcomponents pertenecientes a distintos Components.

La semántica `GENERIC/DISTRIBUTED` de Process **no aplica** a Operaciones Integradas.

### 13.2 Process

Para targets cuyo Tool type es `PROCESS`, cada **Rule específica** declara cómo debe proyectarse en ese target:

```python
class ProcessAlarmProjectionMode(StrEnum):
    GENERIC = "GENERIC"
    DISTRIBUTED = "DISTRIBUTED"
```

Conceptualmente:

```python
AlarmVisualTarget(
    tool_key=...,
    component_keys=(...),
    subcomponents=(...),
    process_projection_mode=ProcessAlarmProjectionMode.GENERIC,
)
```

o:

```python
AlarmVisualTarget(
    tool_key=...,
    component_keys=(...),
    subcomponents=(...),
    process_projection_mode=ProcessAlarmProjectionMode.DISTRIBUTED,
)
```

La propiedad pertenece al **target PROCESS de esa Rule**, no a la Family completa ni a la alarma globalmente.

Una misma Rule puede tener:

```text
Target PROCESS
-> DISTRIBUTED

Target INTEGRATED_OPERATIONS
-> process_projection_mode = None
```

### 13.3 Significado de GENERIC y DISTRIBUTED

B.1 declara intención, no geometría de UI:

```text
GENERIC
-> participa del flujo normal de proyección del Process.

DISTRIBUTED
-> pertenece al conjunto de Rules que el panel Process puede agrupar
   mediante su comportamiento distributed.
```

La evidencia actual proviene de Flotación Selectiva:

```text
0 distributed activas
-> 6 slots normales

1 distributed activa
-> entra al flujo normal de los 6 slots

2+ distributed activas
-> 5 slots normales
-> 1 slot agrupador distributed a la derecha
```

**Esta geometría no pertenece a Alarm Core.**

El contrato B.1 sólo necesita permitir que cada Rule marque su target PROCESS como `GENERIC` o `DISTRIBUTED`.

Cualquier Process futuro puede reutilizar el mismo modo sin que Core conozca su layout concreto.

### 13.4 Strategic

No existe todavía información suficiente para definir comportamiento visual específico de Strategic.

Por tanto:

```text
STRATEGIC
-> no se inventa un projection mode
-> process_projection_mode = None
```

El contrato puede ampliarse en una iteración futura cuando exista evidencia real.

### 13.5 Validación B.2 por Tool type

B.2 resolverá contra Tool Configuration:

```text
Tool type = PROCESS
-> process_projection_mode requerido:
   GENERIC | DISTRIBUTED

Tool type = INTEGRATED_OPERATIONS
-> process_projection_mode = None

Tool type = STRATEGIC
-> process_projection_mode = None
   hasta existir contrato Strategic
```

### 13.6 operator_bucket

`operator_bucket` queda retirado del contrato canónico.

Su responsabilidad histórica queda expresada de forma más precisa mediante:

```text
process_projection_mode
```

No se mantiene alias ni compatibilidad en B.1.

## 14. Ownership de Tool Configuration

Cada Tool es dueña de:

```text
tool_key
tool_type / tier
components[]
subcomponents[]
relaciones component/subcomponent
```

Tipos conocidos:

```text
PROCESS
INTEGRATED_OPERATIONS
STRATEGIC
```

Alarm Configuration sólo guarda referencias.

SharePoint/source-of-truth mantiene las reglas generales del proyecto y Tool Configuration puede proyectarse a Cosmos DB para consumo.

Conceptualmente:

```text
Tool owner
    |
    v
Tool Configuration
    |
    v
Cosmos DB projection
    |
    v
B.2 Configuration Resolution
    |
    +--> valida Tool
    +--> valida Component
    +--> valida Subcomponent
    +--> valida Tool type
    +--> valida process_projection_mode
```

Cosmos es plano de proyección/consumo, no ownership.

## 15. Adoption semantics

Interpretación:

```text
COMPATIBLE
-> conserva occurrence/episode/estado durable.
-> la nueva revisión puede modificar comportamiento desde la adopción o siguiente ciclo.

STRUCTURAL_RESET
-> cambio válido, pero requiere recomponer estructura runtime.

DISABLED
-> Rule sigue definida, sale de ejecución y su occurrence abierta se cierra.

REJECTED / MIGRATION REQUIRED
-> el engine actual no puede adoptar ese cambio con la semántica deseada
   sin evolución explícita.
```

### 15.1 Matriz consolidada

| Campo / cambio | Semántica deseada | Notas |
|---|---|---|
| `rule_name` | COMPATIBLE | Nombre técnico editable; no cambia identidad. |
| `display_name` | COMPATIBLE | Metadata humana. |
| `title` | COMPATIBLE | Contenido estático. |
| `cause_template` | COMPATIBLE | Nueva materialización usa nueva plantilla. |
| `business_category` | COMPATIBLE | Clasificación. |
| `operational_areas` | COMPATIBLE | Clasificación Mina/Planta. |
| `color` | COMPATIBLE | Proyección/negocio, no lifecycle. |
| `is_active: true -> false` | DISABLED | Cierra occurrence de esa Rule; no reset grupal. |
| `visibility_mode` | COMPATIBLE | Delivery decide proyección visible. |
| `is_special_condition` | COMPATIBLE + reconcile | Puede cambiar el efecto de Management vigente. |
| `parameters` | COMPATIBLE | Siguiente evaluación usa nuevos valores. |
| `evaluator_key` | COMPATIBLE deseado | Cambia respecto de R3.5, que hoy lo rechaza. |
| `priority_group` | STRUCTURAL GROUP MIGRATION | Reconciliar grupo de origen + grupo destino. |
| `priority_order` | COMPATIBLE | Priority se recalcula. |
| `criticality` | STRUCTURAL_RESET | Conserva semántica histórica. |
| `kind` | COMPATIBLE deseado | Cambia respecto de R3.5; revisión resultante debe seguir siendo válida. |
| `message_keys` | COMPATIBLE | Cambia opciones futuras de gestión. |

### 15.2 priority_group

No se resetea toda la Family.

La semántica deseada es:

El engine actual aún rechaza esta mutación y deberá evolucionar.
